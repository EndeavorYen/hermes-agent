# Hermes Memory Guardrails and Non-Goals

This document defines the skeptical constraints for the Hermes memory redesign.

Its job is to prevent architecture theater.

---

## Executive stance

Do **not** start by building:
- a graph-first memory system
- a memory operating system
- a large imported memory framework as the new center of truth
- a giant prompt-injected memory block

Hermes already has the right instincts:
- small durable priors
- frozen prompt snapshots
- skills as procedural memory
- opt-in candidate ledger with audited promotion

The redesign should strengthen those instincts, not erase them.

---

## Hard guardrails

## 1. Durable belief requires explicit promotion
Nothing becomes durable Layer 1 because it:
- was retrieved often
- looked semantically close to prior facts
- appeared in a good summary
- was generated by an external framework

A durable belief requires:
- a candidate or explicit durable-write source
- provenance
- explicit routing decision
- allowlisted or reviewed promotion path
- audit trail for success or failure

---

## 2. Retrieval is advisory, not evidence
Retrieved context must never count as fresh evidence by itself.

Rules:
- retrieval does not increment recurrence
- retrieval cannot directly promote durable memory
- retrieved summaries do not count as new support
- graph edges or semantic neighbors do not equal grounded truth

If retrieval changes behavior, that is acceptable.
If retrieval changes truth status by itself, that is a bug.

---

## 3. No mid-session mutation of the prompt prefix
Prompt-cache stability is a hard invariant.

Rules:
- Layer 1 snapshots are frozen for the session or cron run
- mid-session disk writes do not alter the active prefix
- dynamic recall must be injected ephemerally outside the stable system prompt

Any design that requires hot-swapping durable priors into the active prompt is misaligned with Hermes.

---

## 4. Durable write authorities must be enumerated
Write authority should be explicit and short.

Allowed durable-write sources should remain narrow, such as:
- built-in memory tool
- allowlisted cron promotion path
- future explicit review/approval action

Default posture for everything else:
- read-only
- candidate-only
- or discard

Subagents remain memory-isolated by default.
External providers must not become hidden durable authorities.

---

## 5. Contradiction is first-class
A memory architecture that only strengthens will accumulate myths.

Requirements:
- contradictions must be evented
- contradiction counts must remain visible
- contradiction should affect promotion eligibility
- contradiction must not silently erase provenance

Do not bury contradiction only inside a scalar confidence score.

---

## 6. Hidden or empty output must not mutate memory
Current scheduler behavior is directionally correct:
- if a fenced memory payload leaves no visible output after stripping, nothing should be applied

Preserve this principle beyond cron:
- no write-only hidden memory mutation paths
- no stealth memory edits without user-visible or audit-visible evidence

---

## 7. Schema sophistication must lag policy clarity
Do not build rich graph schemas, ontologies, or edge taxonomies before the team can explain:
- how they improve routing
- how they affect promotion
- how they change contradiction handling
- how they improve retrieval quality measurably

If policy is fuzzy, richer schema only hides the fuzziness.

---

## 8. Skills must remain procedural
Do not collapse associative recall into skills.

Why:
- skills are reusable procedures
- recall is situational memory
- mixing them makes both retrieval and governance worse

If an object answers “how to do this repeatedly,” it may be a skill.
If it answers “what matters in this scene,” it belongs in recall.

---

## 9. Most memory should not become Layer 1
The success of the redesign is not measured by how much memory reaches `MEMORY.md` or `USER.md`.

The success metric is:
- better recall
- better routing
- better context relevance
- preserved cache stability
- governed promotion

Layer 1 should remain scarce.

---

## 10. Local auditability beats framework convenience
If an imported framework makes it harder to answer:
- where did this belief come from?
- when was it promoted?
- why was it retrieved now?
- what source supported it?

then it is the wrong center for Hermes.

External frameworks may inspire or optionally plug in.
They should not become the source of uninspectable truth.

---

## What not to build first

### 1. Graph-first memory
Why to avoid first:
- creates strong illusion of structure before evidence quality is solved
- raises ontology and merge burden too early
- makes retrieval look smarter than it is

Allowed later only after:
- strong provenance
- contradiction policy
- routing policy
- measured recall wins

### 2. Memory OS abstraction
Why to defer:
- multiplies abstraction layers before behavior is trustworthy
- makes it harder to identify actual durable-write authority
- risks semantic mismatch across providers

### 3. Imported framework as architecture center
Why to avoid:
- external systems often mix extraction, retrieval, and durable writes
- Hermes already has its own prompt/cache/memory semantics
- framework-led redesign risks forcing Hermes into the framework’s truth model

### 4. Embedding-first retrieval
Why to defer:
- easy to retrieve plausible but wrong context
- hard to debug without strong provenance and evaluation
- lexical, metadata, and recurrence-aware retrieval should come first

### 5. Automatic skill creation from weak evidence
Why to defer:
- procedural memory affects agent behavior directly
- false skills are more dangerous than false context recall
- skill promotion needs stronger review than candidate memory

---

## Minimum viable architecture

The smallest sane memory architecture is:

### Layer 0 — working/session memory
Current transcripts, tool outputs, compression, and task-local context.

### Layer 1 — durable priors
`MEMORY.md` and `USER.md` only.
Small, frozen, high-confidence.

### Layer 2 — candidate + associative recall ledger
Append-only or audit-friendly substrate for:
- observations
- episodes
- candidates
- support/contradiction
- retrieval-oriented associations

### Layer 3 — procedural memory
Skills only.

### Layer 4 — runtime context pack
Ephemeral recall bundle assembled at turn time.

That is enough to build meaningful recall without pretending to solve all memory.

---

## Do now / defer / avoid

## DO NOW
1. Formalize the layered architecture and contracts.
2. Generalize the current cron Layer-2 ledger into the future recall substrate.
3. Add routing contracts that distinguish:
   - prior
   - user
   - episodic
   - context_pack
   - skill
   - discard
4. Build runtime context-pack assembly using the existing ephemeral injection model.
5. Keep durable promotion narrow and audited.
6. Add retrieval logging so recall can be evaluated instead of imagined.

## DEFER
1. graph overlay
2. embedding-heavy retrieval
3. broad provider-led memory mutation
4. automated skill promotion
5. memory OS abstractions

## AVOID
1. turning `MEMORY.md` / `USER.md` into giant RAG dumps
2. making retrieval results look like canonical truth
3. hiding durable writes behind external framework internals
4. mutating prompt prefix mid-session
5. confusing situational recall with procedural memory

---

## Success criteria

A good Hermes memory redesign should make these statements true:
- durable priors stay small and cleaner than before
- scene-triggered recall becomes possible without prompt-prefix bloat
- every candidate and promotion can be audited
- retrieval can be inspected and evaluated
- skills remain focused on procedure
- the runtime preserves prompt-cache stability

If those are not true, the redesign is not done, no matter how sophisticated the storage layer looks.
