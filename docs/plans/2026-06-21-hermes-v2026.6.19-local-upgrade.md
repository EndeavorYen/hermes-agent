## Delta Classification

### port-as-config/plugin/skill

- Keep `rtk-rewrite` as a runtime plugin. Acceptance: a terminal tool call is
  rewritten through `rtk rewrite` when RTK returns a changed command, and the
  plugin fails open when RTK is missing or times out.
- Keep `image-reference-library` as a runtime plugin. Acceptance: enabled plugin
  registers `image_ref_*` tools and any local skills without patching core.
- Keep `visual-arsenal` as a runtime plugin. Acceptance: enabled plugin
  registers visual arsenal tools and Slack hooks, and can use upstream image
  generation/editing APIs without private core patches.
- Keep local `config.yaml` policy in runtime state, not committed secrets.
  Acceptance: live config still selects `grok-4.3`/`xai-oauth`,
  `gpt-5.4`/`openai-codex` fallback, Slack, image/video providers, and enabled
  plugins.

### upstream-equivalent candidates

- `image_generate` image-to-image/editing: upstream `v2026.6.19` now has native
  support. Acceptance: keep upstream implementation unless local reference
  image conditioning or xAI/OpenAI-Codex delivery behavior is still missing and
  proven by a failing test.
- Memory batch operations and quota behavior: upstream now has atomic memory
  batch operations. Acceptance: keep only the local non-retryable quota guard if
  upstream still retries or hides the failure class.
- Background subagents: upstream now has `delegate_task(background=true)`.
  Acceptance: discard local equivalents unless a live contract remains.

### port-core-required candidates

- Local reference image conditioning and local reference image alias resolution,
  if upstream editing support does not preserve the local `image_gen`
  `local_reference_images` contract.
- xAI video routing and image-to-video behavior, if upstream lacks the exact
  Grok Imagine video path required by live visual package workflows.
- Slack visual delivery provenance/dedupe, if runtime Visual Arsenal and visual
  agent packages cannot link generated media back to the Slack thread through
  plugin hooks alone.
- Visual agent self smoke, if it remains the cheapest reliable pre-cutover proof
  for visual package workflows.

### discard until proven otherwise

- Release email mapping and historical archive docs that are not needed for the
  new integration branch.
- Core hook or prompt changes that only support Raphael/visual behavior but can
  be moved into a plugin hook or existing upstream extension point.
- Any local patch with only historical rationale and no current runtime config,
  job, plugin, command, test, or live workflow using it.

### upstream-pr-candidate

- Generic bug fixes that are not personal policy: memory quota non-retryable
  classification, legacy hook compatibility, dashboard/plugin config reader
  safety, and image/video provider fixes if still missing upstream.
- Do not open upstream PRs from this branch unless explicitly requested. Split
  each generic fix into a small candidate branch first.

## Future Upgrade Notes

Use this plan shape for later Hermes release upgrades, but keep the evidence
short. The reusable lesson from this cutover is to prove the real workflow while
avoiding a growing release diary.

- Prepare a low-noise Slack smoke target before cutover. Prefer one actual
  outbound delivery proof to that target after the upgraded gateway reconnects.
  If sending a live message would be disruptive, record that decision and pair
  Slack Socket Mode logs with targeted Slack delivery tests instead.
- Use a fixed evidence template:
  - upstream tag and integration branch
  - previous live branch and rollback branch
  - kept local contracts and why they still earn their place
  - targeted tests and pass counts
  - provider/fallback/auth proof
  - launchd plist match, new gateway PID, and cron status
  - Slack outbound proof or documented non-send fallback
  - reference-image and visual package proof
  - remaining untracked or deferred cleanup items

  this machine, `FAL_KEY` is not required for the local v2026.6.19 upgrade
  because the active runtime contract is `image_gen.provider: openai-codex`
  and `video_gen.provider: xai`. A `configure_video_fallback_provider` action
  can remain useful diagnostic context, but it is not a cutover prerequisite
  unless `config.yaml` selects that provider or the operator explicitly opts in.
