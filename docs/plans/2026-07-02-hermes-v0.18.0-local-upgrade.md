# Hermes v0.18.0 Local Upgrade Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade Simon's local Hermes runtime from the current
`upgrade/hermes-v2026.6.19-local` line to upstream Hermes Agent `v0.18.0`
without regressing daily Slack, provider fallback, RTK, Raphael, or visual
agent workflows.

**Architecture:** Start from upstream tag `v2026.7.1` (the source tag for
Hermes Agent `v0.18.0`) in an isolated worktree, then intentionally port only
local behavior that still has a current runtime contract. Prefer upstream
`v0.18.0` implementations for MoA, goal verification, learning/journey,
background subagents, gateway drain/scale-to-zero, and security hardening
unless a focused compatibility test proves a local patch is still required.

**Tech Stack:** Python 3.11-3.13, `uv`, `pytest`, `scripts/run_tests.sh`,
Hermes gateway/launchd, Slack Socket Mode, local runtime plugins, xAI/Grok,
OpenAI Codex, visual agent tooling.

## Non-Negotiable Guardrails

- Do not merge, rebase, stash, reset, or clean the current dirty worktree as a
  first step. Inventory it first and preserve enough evidence to restore every
  local change.
- Do not start from the current dirty branch. Create an isolated upstream-based
  worktree for `v2026.7.1`.
- Use upstream as the base. Treat the local `v2026.6.19` port and Raphael/visual
  WIP as technical debt to audit, not behavior to preserve by default.
- Keep private runtime evidence local. Do not commit provider responses,
  generated media, Slack artifacts, ledgers, prompt traces, caches, `.env`, or
  platform metadata.
- Push integration branches to `origin` only. Do not create upstream issues or
  PRs unless explicitly requested.
- Every kept core patch needs a focused test, an upstream-equivalent audit, an
  upstream PR candidacy decision, and an exit condition.
