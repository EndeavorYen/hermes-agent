Layer-2 currently touches:

- `agent/layer2_memory_provider.py`
- `agent/layer2_recall.py`
- `memory/layer2_store.py`
- `memory/layer2_consolidate.py`

- `agent/prompt_builder.py`
- `model_tools.py`
- `toolsets.py`
- `cron/jobs.py`
- `cron/scheduler.py`

### Alignment direction

Hermes v2026.4.23 has stronger plugin and memory-provider surfaces. Layer-2 should move toward plugin/provider/tool boundaries instead of hardcoded core branches.

Keep core only for generic extension points:

- memory provider orchestration;
- safe memory context injection;
- generic tool policy hooks;
- generic cron post-response hooks.

Move custom Layer-2 logic toward plugin/provider ownership:

- provider and recall implementation;
- Layer-2 write/review tools;
- `hermes-layer2` fenced payload parsing;
- prompt guidance specific to candidate/episode/context-pack writes.

### Risks

- `layer2` is currently name-special-cased in core.
- `layer2_memory` has multiple registration/routing surfaces.
- Cron direct-write policy is correct but hardcoded.
- Store path under `cron/layer2_memory.sqlite3` is profile-safe but semantically misleading for chat/operator writes.
- Durable promotion path must remain explicit and gated.

### Next slices

1. **Layer-2 provider pluginization**
   - Move provider/recall into plugin or provider package.
   - Replace provider-name special casing with generic provider metadata.
   - Tests: provider discovery, availability, non-external provider metadata, context-pack formatting.

2. **Layer-2 tool registration cleanup**
   - Register Layer-2 tools via plugin/provider surfaces instead of core toolsets where possible.
   - Tests: tool present only when plugin/provider enabled; absent when disabled; routing receives session/tool-call/source refs.

3. **Cron memory-pipeline hook extraction**
   - Replace Layer-2-specific scheduler branches with generic cron response hooks.
   - Tests: fake plugin prompt/response hook; no-op when job not opted in; direct durable memory writes remain blocked.

## Phase C.2: Loop/autonomy/delegation alignment

### Current custom surface

Custom loop/autonomy code currently touches:

- `gateway/run.py`
- `hermes_cli/commands.py`
- `hermes_cli/loop.py`
- `hermes_loop/runtime.py`
- `hermes_loop/store.py`
- `tests/hermes_loop/*`
- `tests/gateway/test_loop_recovery.py`

### Alignment direction

v2026.4.23 added clearer delegation/orchestrator concepts:

- `leaf` vs `orchestrator` subagent role;
- `delegation.max_spawn_depth`;
- sibling file coordination.

Custom `/loop` should remain a persisted continuation control plane, but it needs an explicit contract with delegation so that loop turns and nested subagents do not multiply budgets invisibly.

### Risks

- Two orchestrators currently exist: custom `/loop` and delegation orchestrator role.
- Budget explosion: loop turns × max spawn depth × sibling workers × timeouts.
- File coordination is process-local, while loop recovery is persisted.
- `gateway/run.py` has a large loop integration surface.
- Checkpoint writes should be made more atomic and lease-aware.
- LLM progress verifier is useful but should not be the only progress authority.

### Next slices

1. **Loop × delegation budget contract**
   - Add explicit policy for whether loop turns may use delegation and at what depth/concurrency.
   - Tests: default loop does not grant nested orchestration; explicit opt-in does; budget cap stops/refuses unsafe envelopes.

2. **Atomic loop persistence and recovery lease**
   - Add atomic checkpoint writes and run-epoch/lease ownership.
   - Tests: corrupt checkpoint fails closed; two runners cannot double-resume; stale executing state pauses instead of blind replay.

3. **Recovered-loop file-safety bridge**
   - Persist or enforce re-read policy after recovery before writes.
   - Tests: file changed across restart forces re-read/block; delegated sibling edit surfaces stale-write warning.

## Phase C.3: Webhook/dashboard/Taiwan-Shadow alignment

### Current useful upstream surfaces

v2026.4.23 already has a low-risk zero-LLM path:

- `gateway/platforms/webhook.py` supports `deliver_only` routes.
- `hermes_cli/webhook.py` supports `hermes webhook subscribe ... --deliver-only`.
- `tests/gateway/test_webhook_deliver_only.py` covers no-agent delivery, idempotency, auth/rate-limit behavior.

Dashboard/plugin surfaces are also ready for internal views:

- plugin manifests under `dashboard/manifest.json`;
- served assets under `/dashboard-plugins/<name>/...`;
- plugin APIs under `/api/plugins/<name>/...`;
- web plugin tabs/slots via the dashboard SDK.

### Alignment direction

Use direct-delivery for concise Taiwan/Shadow notifications that do not need reasoning. Use dashboard/plugin views for internal state and richer review.

Preferred first POC:

- Create a `taiwan-shadow-alerts` webhook subscription with `deliver_only`.
- Upstream monitor emits a pre-rendered concise Slack mrkdwn card.
- Include stable event id / idempotency key.
- Do not wake the LLM for pure notification events.

Slack note:

- Generic Slack sends are text/mrkdwn today, not generic Block Kit.
- Start with compact mrkdwn cards; only add Block Kit later if needed.

### Risks

- Direct-delivery fields must be sanitized/truncated by the producer.
- Dashboard plugin APIs are local-first; do not expose publicly without auth.
- Producer should provide stable idempotency keys, not rely on timestamp fallback.
- Layer-2 dashboard views must handle missing/corrupt SQLite/state files gracefully.

### Next slices

1. **Zero-LLM Taiwan/Shadow notification route**
   - Define event schema: `event_id`, `severity`, `title`, `score`, `state`, `layer2_summary`, `url`.
   - Configure deliver-only webhook.
   - Tests: duplicate event id sends once; missing adapter returns 502; formatting stays within Slack length budget.

2. **`taiwan-shadow` dashboard plugin tab**
   - Show monitor status, shadow scorecard, Layer-2 counts, state-sync freshness, notification health.
   - Tests: plugin discovery; safe empty state; API caps records and hides secrets; frontend loading/empty/error states.

3. **Layer-2 scorecard/state-sync audit bridge**
   - Write observations/context packs directly from monitor/state-sync without waking LLM.
   - Tests: idempotency by source event id; subject scope filters; bounded query pack; corrupt/missing state handled.
